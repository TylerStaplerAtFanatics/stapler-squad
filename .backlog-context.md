# Bad UX when backlog actions linger (Priority 3 | Status: in_progress)

## Description
When backlog actions like hitting, apply, autonomously or any of the other buttons. Take a while to kick off the UI doesn't give any visual indication that the button has been activated. Can we make sure that our buttons give visual indication that they are currently running and if they fail or whatever we get a pop-up snack bar type message

## Acceptance Criteria
0. [✓] Clicking any backlog action button shows a visible pending/running indicator (spinner + label change) on that specific button while its request is in flight
1. [✓] Sibling buttons in the same mutually-exclusive group remain disabled (not spinning) while one action is in flight
2. [✓] transitionStatus/spawnSessionFromItem/cancelTriage rethrow on RPC failure instead of silently swallowing it, so failures are catchable
3. [✓] When any action fails (including previously-swallowed ones), a toast/snackbar with a clear error message appears
4. [✓] When an action succeeds, a success toast confirms it
5. [✓] Action toasts do not add permanent entries to the notification bell panel or audit log
6. [✓] Toasts auto-dismiss and do not block the UI indefinitely
7. [✓] Repeated failures of the same action do not stack duplicate toasts, and concurrent toasts for different items don't collide/replace each other
8. [✓] Board-level per-card action buttons (board/page.tsx, BacklogItemCard.tsx) show independent per-card pending state without freezing other cards
9. [✓] 'Run Autonomously' shows only a brief kickoff-acknowledged spinner and hands off via toast, rather than blocking until the background session completes
10. [✓] No setState-after-unmount warnings occur if the detail panel closes while an action is in flight
11. [✓] No new WCAG AA violations are introduced by the spinner/toast markup
