# Architecture Review: backlog-configurable-pipeline
**Date**: 2026-07-15
**Verdict**: CONCERNS

## Constitution Violations
- N/A — `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo (confirmed via `ls docs/adr/`; the directory contains ADR-001 through ADR-023 in various numbering schemes but no ADR-000 or constitution document).

## Blockers

- [ ] **Epic 1.6 / `ItemSessionSummary.PipelineModeSnapshot`** — the snapshot mechanism does not actually snapshot mode *content*, only the mode *slug*, which fails the stated goal it's built to satisfy. The Domain Glossary entry for `ItemSessionSummary.PipelineModeSnapshot` explicitly promises "the resolved mode identifier (**and a content version/hash**)," and the Pattern Decisions table justifies "Immutable-after-first-triage-session" by claiming it prevents "an in-flight item's triage and review stages silently run[ning] under two different mode definitions (**or definitions-as-they-existed-at-different-times**)." But Epic 1.6's actual schema (Story 1.6.1) adds exactly one field, `field.String("pipeline_mode_snapshot")` — the slug, nothing else. Compare this to the precedent it claims to mirror: `AcSnapshot` (`session/repository.go:288`) stores the full `AcCriteriaJSON` *content*, not a reference to a criteria-set ID — that's precisely why it protects against drift. A slug-only snapshot only protects against the item's own `pipeline_mode` field changing later (case (a)); it does nothing to protect against the *referenced mode's own template content being edited later* (case (b)) — which is the harder, DB-mutability-specific risk this whole ADR exists to manage (see requirements.md's Open Questions: "an item's stored mode-slug could point at a mode whose content changed after the item started... Phase 3 must decide whether to snapshot resolved mode content... or always resolve live"). Story 3.4.1 confirms the bug concretely: the "what ran" UI resolves the snapshot by "matching `slug`" against "the currently-fetched mode list" — i.e. it does a *live* lookup of the mode's current name/content by slug, not a frozen read. If an operator edits `"quick"`'s `triage_prompt_template` next week, every historical session that ran under `"quick"` will silently display the *new* content as if it always ran that way — exactly the "silent retroactive change" scenario the field's own `.Comment()` text (Story 1.6.1's acceptance criteria) says it exists to prevent: *"so later edits to the item's live pipeline_mode, or **to the mode definition itself**, don't retroactively change what this session is shown to have run."* The implementation directly contradicts its own doc comment.
  - **Remediation**: either (a) store a real content snapshot — cheapest correct option is a hash of the 9 rendered template fields at resolution time (`pipeline_mode_snapshot_hash string`) plus the slug, and have the "what ran" UI show "mode X (content since changed)" when the live mode's current hash doesn't match the stored one, or (b) snapshot the fully-rendered prompt/command content itself (heavier, but exactly mirrors `AcSnapshot`'s full-content approach) into a new small table/JSON column, or (c) explicitly descope the content-drift protection for this phase and correct the Domain Glossary/Pattern Decisions/field-comment text to stop promising something the schema doesn't deliver — silently shipping a comment that lies about the guarantee is worse than not having the guarantee. Whichever is chosen, `pipeline_mode_snapshot_version` is even referenced in the Migration Plan file list line ("`pipeline_mode_snapshot`/`pipeline_mode_snapshot_version` fields on `session/ent/schema/item_session.go`" — Migration Plan, line ~69) but then silently dropped from Epic 1.6's actual acceptance criteria and task list, which only ever add `pipeline_mode_snapshot`. This is not just a design gap, it's an internal plan inconsistency — the Migration Plan and Epic 1.6 disagree with each other about how many columns are being added. Fix before Story 1.6.1 starts.

- [ ] **Pattern Decisions / `PipelineEngine` interface location — factually incorrect precedent claim** — the plan's stated justification for placing `PipelineEngine` in the `session` package is: *"`session` is consumed by two independent packages (`server/services` and `session` itself, via `BacklogLifecycleListener`)... `WorkflowEngine` already establishes this exact precedent in this exact codebase."* This is false. Direct code inspection (`grep -rn "WorkflowEngine" server/services/*.go session/*.go`) shows `WorkflowEngine` has **exactly one consumer in the entire codebase**: `server/services/backlog_service.go` (field `engine session.WorkflowEngine`, constructor param, one nil-guard fallback to `NewDefaultWorkflowEngine()`). `session.BacklogLifecycleListener` and `session.ReviewGateRunner` (`session/backlog_lifecycle.go`, `session/review_gate.go`) reference `WorkflowEngine` **zero times** — confirmed by grep returning no matches in either file. So `WorkflowEngine` is not a multi-consumer shared seam at all; it is a single-implementation, single-consumer interface with **zero test doubles anywhere in the repo** (`grep -rln "WorkflowEngine" --include="*_test.go" .` returns nothing) — meaning it isn't even used for test substitutability, the other common legitimate reason to keep an interface with one impl. `WorkflowEngine` is itself already a clean instance of interface-pollution-checklist smell #1 ("speculative interface — exactly one implementation and no near-term second one") *and* smell #2 ("interface defined next to its implementation" — both `WorkflowEngine` and `DefaultWorkflowEngine` live in `session/workflow_engine.go`). The plan cites this as a validated precedent to copy; it is actually an existing, uncorrected violation being used to justify compounding the same violation in a new, larger seam.
  - Note for calibration: `PipelineEngine` as actually specified in Epic 1.5 (Story 1.5.1c adds it to `ReviewGateRunner`, which lives in the `session` package) *does* end up with two real cross-package-boundary consumers (`server/services.BacklogService` and `session.ReviewGateRunner`) — so the underlying placement decision (put it in `session`) is independently defensible on its own facts. The problem is specifically the plan's justification, not necessarily its conclusion.
  - **Remediation**: rewrite the Pattern Decisions row to justify placement on `PipelineEngine`'s own actual two-consumer shape (`BacklogService` + `ReviewGateRunner`, verified by Story 1.5.1's own acceptance criteria), not on a fabricated `WorkflowEngine` precedent. Separately — out of scope for this feature but worth a follow-up ticket — `WorkflowEngine`'s single-implementation, zero-test-double status should be revisited under the interface-pollution checklist; it should not be cited as a positive precedent in future plans until it is.

## Concerns

- [ ] **Lens 3 / GoF pattern appropriateness — `PipelineEngine` as a single-implementation interface** — `PipelineEngine` will ship with exactly one production implementation (`CachingPipelineEngine`) for the foreseeable future (no second implementation is planned anywhere in this plan's 4 phases). Per `.claude/rules/interface-pollution-checklist.md` smell #1, this is a real smell on its face. However, unlike `WorkflowEngine` (see Blockers above), this case has two mitigating factors the checklist itself would accept: (1) it has two genuine cross-package consumers (`server/services.BacklogService`, `session.ReviewGateRunner`), which is the actual Go-idiomatic reason to define an interface rather than expose a concrete type — not "future swappability," but "the consuming packages shouldn't both import a private constructor of a type from a fourth location," and (2) Story 1.5.1d explicitly plans test-double substitution at ~20 test call sites (`session/review_gate_test.go`, `session/review_gate_integration_test.go`), meaning it *will* have fakes, unlike `WorkflowEngine`. Verdict: **defensible, not a violation**, but only because of the two-consumer + test-double facts — the plan should say so explicitly rather than leaning on the (incorrect) `WorkflowEngine` precedent (see Blocker above), because if either of those two facts changes (e.g., `ReviewGateRunner`'s dependency is dropped in a later refactor, leaving only `BacklogService`), the interface should be collapsed back to a concrete type at that point.

- [ ] **Lens 1.1 / `CachingPipelineEngine` — four content-generation responsibilities behind one type** — `CachingPipelineEngine` combines: (a) cache-hit/miss resolution logic, (b) fail-closed fallback + Warn logging, (c) template rendering (`renderTemplate`), and (d) four largely-independent content-generation methods (`SlashCommandSet`, `TriagePromptFor`, `ReviewPromptFor`, `InitialPromptFor`) each delegating to a different default-path free function. This is borderline but net acceptable: (a)+(b)+(c) are genuinely one cohesive "resolve-a-mode-and-render-it" responsibility shared identically across all 4 methods (same cache, same fallback pattern, same renderer) — splitting them apart would mean duplicating the cache-lookup + Warn-fallback boilerplate 4 times, which is worse. The 4 content methods are more debatable — they don't share business logic with each other, only the resolution *mechanism*. This is consistent with `DefaultWorkflowEngine`'s existing shape (3 methods on one type, sharing one backing map) so it's locally idiomatic, but it does mean `CachingPipelineEngine` will keep growing every time a new "which content varies by mode" call site is discovered (this already happened once — `InitialPromptFor` was added mid-planning specifically to avoid the seam being cosmetic for autonomous mode, per the Pattern Decisions table). **Recommendation**: not a blocking issue for Phase 1, but if a 5th or 6th mode-varying call site is discovered later (a real risk flagged in the plan's own Rabbit Holes section re: `autonomous_driver.go`), reconsider extracting the shared resolve+fallback+render mechanism into a small unexported helper (e.g. `resolve[T any](item, cache, renderFn) (T, bool)`) that each of the 4 public methods calls, rather than letting `CachingPipelineEngine` keep accreting near-duplicate method bodies. Track this as a trigger condition, not an immediate refactor.

- [ ] **Lens 1.4 / Testability of `atomic.Pointer[map[string]resolvedPipelineMode]`** — Task 1.3.2c's stated race test only asserts "no torn/partial read" under concurrent `Get`+`Invalidate`, which `atomic.Pointer` trivially guarantees by construction (an atomic load of a pointer either gets the whole old map or the whole new map — there's no way to write a test that would fail this if the code is correct, making the acceptance criterion close to untestable-as-stated / tautological). The design's actual hard-to-test failure mode is different and unaddressed: a caller that does `snapshot := cache.Get(slug)` and then, across an `await`/goroutine-yield/long-running LLM call, uses fields off that snapshot — is it guaranteed the snapshot is self-consistent even after 3 subsequent `Invalidate` calls happen concurrently? Yes, by copy-on-write construction (the caller holds its own `resolvedPipelineMode` value, not a pointer into the live map) — but the plan doesn't call this out explicitly as the actual invariant being protected, and the "torn read" framing in Story 1.3.2's acceptance criteria undersells what's really being guaranteed (immutable point-in-time snapshots surviving concurrent invalidation across long-lived callers, e.g. an in-flight LLM call reading `resolvedPipelineMode` fields hundreds of ms after `Get` returned). **Recommendation**: rewrite Task 1.3.2c's test to explicitly assert this scenario — hold a `Get()` result across a simulated `Invalidate()`, then assert the held value's fields are unchanged — rather than the weaker "no `-race` failure" framing, which mostly just verifies `atomic.Pointer` itself works (a stdlib guarantee, not something this design needs to prove).

- [ ] **Lens 2.7 / Parse-at-boundary — validation timing gap between Phase 1 and Phase 2** — Phase 1 (Epic 1.4) wires the `optional string pipeline_mode` field through Create/Update RPC handlers with **presence gating only** (correctly closes the clobbering bug), but **no format/slug validation** — `ValidatePipelineModeContent` doesn't ship until Epic 2.3 (Phase 2, several epics later). Between Phase 1 landing and Phase 2 landing, `BacklogItemData.PipelineMode` is writable via `UpdateBacklogItem` with an arbitrary string (any slug, valid or not) — but per Story 1.7.3, at the end of Phase 1 there's no UI/CRUD surface to create a matching `PipelineMode` row yet, so every non-empty value written during this window is guaranteed to be an unresolved slug, hitting the Warn-fallback path on every read. This is low-risk in practice (single-operator tool, and the fail-closed path handles it correctly) but is worth stating explicitly as an accepted, temporary gap rather than leaving it implicit — a future reader auditing "when is `pipeline_mode` validated" could reasonably expect Phase 1 to already reject garbage values at the RPC boundary, given the NFR's "structural integrity, not access control" framing applies from the start, not just from Phase 2 onward.

- [ ] **Lens 3.10 / API contract stability — `PipelineModeRepository` returning `*ent.PipelineMode` directly** — the plan explicitly chooses to leak the ent-generated type through the repository interface (Pattern Decisions table, "no current consumer needs decoupling from ent... adding a parallel DTO here would be a forwarding-only wrapper"). This mirrors `WorkflowRepository`'s existing convention, so it's locally consistent, but it does mean every consumer of `PipelineModeRepository` (currently: `CachingPipelineEngine`, and the 5 new RPC handlers in Epic 2.2) is coupled to ent's generated struct shape — a future ent regeneration that renames/retypes a field (e.g. switching a `string` to a custom `field.Enum`-backed type) becomes a breaking change across both the caching engine and every RPC handler simultaneously, with no interface boundary absorbing it. Acceptable given the existing codebase convention, but flagging because this compounds — every new ent-backed repository in this style makes a future "decouple domain from ent" refactor larger. Not a blocker; just don't extend this convention indefinitely without revisiting it.

## Nitpicks

- Epic 1.3.3d's `renderTemplate` allow-list currently only enumerates `item_id` and `criteria_index` as recognized placeholders, but the Domain Glossary's content-template field list (9 fields covering triage/review/initial prompts and 6 command files) plausibly needs more placeholders than just those two (e.g. an item's title, description, or AC criteria text) to be useful in practice — the plan doesn't enumerate the full placeholder set anywhere, which risks Epic 4.1's "prove the seam isn't cosmetic" milestone being awkward to satisfy with only 2 available substitutions. Worth a quick pass before Story 1.3.3d to confirm 2 placeholders is intentionally minimal-for-Phase-1 (plausible) rather than an oversight.
- The Unresolved Questions item about write-time vs. render-time `{{...}}` placeholder validation (blocks Story 2.3.1) defaults to "write-time allow-list rejection," but Task 1.3.3d (Phase 1, shipped before Phase 2's validation exists) implements the opposite — "unrecognized placeholder tokens are left as-is" at render time. This isn't a contradiction (Phase 1 has no validation surface yet; Phase 2 adds one later) but the plan doesn't explicitly say Task 1.3.3d's render-time leniency is superseded/tightened by Story 2.3.1 — worth one clarifying sentence so an implementer doesn't read them as conflicting requirements.
- Story 1.3.4b's task description hedges between two options ("deferred to Epic 1.5... OR do both in the same task if under the 3-5 file cap") rather than committing to one — minor, but every other task in the plan commits to a single concrete scope; this one task reads like unresolved planning residue.
